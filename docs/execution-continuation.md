# Execution continuation

Both `/v1/responses` and `/v1/chat/completions` use the same scoped identity as audit grouping to find an execution checkpoint: API Key, endpoint, client originator, installation ID (when supplied), client thread ID, and conversation category. Conflicting identifiers, incomplete captures and title-generation requests do not auto-resume. IP addresses, cache hits and `prompt_cache_key` alone never authorize Thread reuse. History-only correlation remains observational.

Selection priority is authenticated pending tool `call_id`, explicit `previous_response_id`, then guarded automatic continuation. A pending result cannot change its Worker/Thread or client conversation. Explicit previous IDs retain their existing ownership/expiry checks and error behavior.

Automatic continuation requires a completed checkpoint, an active ResponseBinding, an available compatible Worker, identical model/instructions/tool definitions/tool choice/output schema, and full input history whose canonical prefix matches the checkpoint. Transport message IDs, annotations and text-block wrappers do not affect comparison. The appended suffix must contain a user message and no replayed assistant/tool calls. Only that suffix goes to `turn/start`; the original full request stays in the audit log and remains available for a safe rebuild. No full replay is appended to an existing Thread.

Missing checkpoints (including sessions predating deployment), edited/compacted histories, changed configuration, released bindings and unavailable Workers start a new Thread using the full input. Subsequent compatible turns can reuse that new Thread. An automatic `thread/resume` rejection may rebuild before `turn/start`; failures after a turn may have begun never trigger replay on another Worker. New/rebuilt conversations use the existing Worker scheduler and cache affinity. Successfully resumed conversations stay on their bound Worker and reuse the existing WS pool.

The `execution_sessions` table stores canonical history hashes, not duplicate prompt text. It is created by the normal `Base.metadata.create_all` startup path (`AUTO_CREATE_SCHEMA=true`). Operators managing schema externally must create this table from the model before enabling the feature. A short row-lock transaction claims a 90-second fenced lease; a heartbeat renews it every 20 seconds without holding a DB connection for model execution. Concurrent requests to the same logical conversation receive 409 `conversation_busy`. A suspended client tool must receive its result before a new user turn; it retains the existing 300-second in-process continuation limit. Expired/interrupted owners cannot overwrite newer checkpoints. Cancellation invalidates the checkpoint. Completed checkpoints persist across gateway restarts; suspended tool RPCs do not.

Checkpoint updates, usage and ResponseBinding creation commit together before the terminal HTTP/SSE response. Usage evidence includes `execution.action`, `execution.reason` and the previous Thread ID, distinguishing resumed, rebuilt, explicit and tool continuations. Thread-level cumulative usage must not be billed repeatedly; per-turn accounting uses current-turn events and last-call/delta counters.

`CODEX_GATEWAY_EXECUTION_RESUME_ENABLED=true` enables this by default. Set it to `false` and restart the gateway to disable automatic continuation while retaining existing explicit response/tool continuation behavior. Worker security policy is applied on every start/resume/turn and is never derived from client configuration.

## Retention and invalidation

Ordinary checkpoints and ResponseBindings no longer expire by elapsed time. The former `CODEX_GATEWAY_RESPONSE_BINDING_TTL_HOURS` option is ignored. Migration reactivates only bindings previously expired automatically with the exact reason `Session TTL expired`; manually invalidated bindings stay invalid. Old expiry dates are cleared. Key active sessions include only logical conversations last used within two hours, without deleting older data. The page retains its flat Thread routing table and labels bindings as restored on demand.

Administrative release, Key deletion, Worker deletion and observed account changes invalidate execution leases and bindings in one transaction. Worker login identity has a monotonically increasing execution generation; forced re-login increments it even for the same account. Late writers cannot recreate bindings after a generation change or a revoked lease. Invalid bindings are retained for diagnosis.

A `waiting_tool` checkpoint blocks new user turns only while its actual in-process tool run is present and within the five-minute deadline. If the run is gone, a new user turn with verified full history can rebuild immediately; an orphaned standalone tool result is rejected and never re-executed. Live waits return `conversation_waiting_tool`; concurrent HTTP execution returns `conversation_busy`; lost calls return `client_tool_call_unavailable`; known duplicate results return `client_tool_result_duplicate`. Recent consumed IDs are held in a bounded in-process cache; after restart an unresolvable call is reported unavailable, not guessed to be a duplicate. Rejection code and message are stored in conversation evidence.

If automatic resume fails before `turn/start`, the old binding is marked broken and full input is used to start a replacement. A pre-turn Worker connection failure may retry once on another eligible Worker. Failures after execution may have started are never replayed automatically. If no eligible Worker is available, a clear error is returned; acceptance cannot be guaranteed during an upstream outage. WS idle recycling, five-minute tool deadlines and the 90-second renewable execution lease remain independent of binding retention.
