# 2026-10-13 repair validation

Release: `repairs-20261013-r3`. Production rollout passed on both nodes on 2026-10-13: app-1 at 12:53:21 UTC and app-2 at 12:55:27 UTC. Both live health checks also passed after rollout.

This document was updated after deployment; the original release archive and its manifest remain unchanged.

## Implemented changes

- Preserve tool protocol error codes and HTTP statuses through backend and cross-node forwarding.
- Keep SSE connections active every 15 seconds without restarting or cancelling the provider iterator; translate heartbeat comments to native Claude ping events.
- Accept completed web-search history without an optional call ID, and the text-only search content option.
- Allow Claude structured output together with client tools in both gateway and Worker validation.
- Distinguish expired, cancelled and duplicate client-tool submissions. Record expiry timing and correlation IDs. Keep public tool-result TTL at 300 seconds and give the Worker a 330-second transport grace window.
- Apply existing verified-history recovery to the new expired/cancelled codes, without re-executing client tools.
- Retain safe Claude result diagnostics, including version incompatibility and malformed model tool calls. Avoid quarantining healthy Workers for request errors.
- Add request/Worker correlation and exception logging for previously opaque backend failures.
- Reject empty model names and direct invalid model requests to the exact IDs in `/v1/models`; no speculative aliases.

The earlier capacity release remains in place: Claude 10 active turns per Key × Worker and 40 per Worker, with overload-aware recent-Worker affinity.

## Confirmed internal MCP timeout

The 190-second test on revision r2 failed after a successful initial tool call. The CLI transcript recorded the MCP tool call at 12:31:54.630 UTC and an error result, "The operation timed out.", at 12:32:54.691 UTC. The gateway later received HTTP 409 from Worker /tool-result and reported 502.

The installed CLI uses a default 60,000 ms MCP HTTP first-byte budget unless a server timeout or MCP_TOOL_TIMEOUT overrides it. Revision r3 sets the relay server timeout, MCP_TOOL_TIMEOUT and CLAUDE_CODE_MCP_TOOL_IDLE_TIMEOUT to 360,000 ms, beyond the 300-second public deadline and 330-second relay deadline. A Worker tool-result 409 now becomes client_tool_call_unavailable (400/request), without quarantining the Worker or replaying the tool.

This confirms the reported one-minute tool failure mechanism; it is distinct from the six external 180-second streaming interruptions below.

## Incident findings and limits

Four pfSense nodes were inspected using the authorized admin SSH account. Gateway backend timeouts are 1,200,000 ms. Shared frontend client timeouts are 300,000 or 600,000 ms. No 180-second setting was found; the inspected active HAProxy process uses the checked configuration path.

The six observed 180.2–180.8-second interruptions were streaming requests with `claude-cli/2.1.296 (external, claude-vscode, agent-sdk/0.3.296)`, JS SDK headers and a declared 600-second timeout. These records do not establish Python concurrent requests as the cause. Heartbeats address idle transport exposure; the exact disconnect origin remains unproven.

Post-release external idle-stream validation passed through the public production DNS/TLS endpoint from the operator host. Each request used a separate temporary, budget-limited key pinned to a production Claude Worker. A detached watchdog paused only that key’s newly created CLI child for 210 seconds and resumed it automatically; the Worker service and other sessions were not paused.

| Protocol | Total duration | Heartbeats | Maximum receive gap | Result |
| --- | --- | --- | --- | --- |
| Responses | 211.99 s | 14 | 15.00 s | response.completed, expected answer |
| Native Messages | 211.95 s | 14 | 15.00 s | message_stop, expected answer |

Response IDs: `resp_2b6ea01a11c646d6a93cb336eb86fb9c` and `resp_5f18061330714dc38e40dd4a8d78a308`. Both children resumed and temporary keys were disabled. This demonstrates that the tested public route survives more than 180 seconds without model output when heartbeats are enabled. It does not identify the source of the historical disconnects or cover every customer network/client version.

The installed Claude Code 2.1.291 client also passed the same controlled 210-second pause through the public endpoint in bare mode, with tools disabled and no client timeout override. It completed successfully in 212.30 seconds and returned the expected answer. Production audit contains exactly one successful request for this test key (`resp_11719e45d5a14d1ca163320dbdb227be`, 211707 ms), so success was not obtained through an observed 180-second failure followed by a gateway request retry. All three controlled tests have HTTP 200/no error audit records, and all three keys were independently verified disabled. Historical client version 2.1.296 and the original customer network were not reproduced.

Earlier attempts to induce a long request by requesting large structured output ended before 180 seconds and are not counted as passing long-idle tests. One returned a model execution failure and one an execution conflict; their temporary keys were disabled. A connection attempt from a production container to the public address timed out before HTTP, so the successful public-route tests ran from the operator host.

Synthetic requests containing legacy billing metadata and clean requests both succeeded before this repair. Therefore legacy metadata alone is not a verified cause of the reported outdated CLI rejection. Customer prompts are not rewritten based on that hypothesis.

Six older backend 502 records lacked sufficient underlying exception detail to establish individual root causes. New logging improves diagnosis of recurrence; it does not retroactively prove those causes.

## Rollout and rollback

The release runner lives in `/tmp/codex-repairs-prod-20261013-r3` on the operator host and both production nodes. It records `status.json` locally and `node-status.json` per node. Each node runs independently under systemd, so conversation interruption does not stop deployment. The final runner status is `passed`; no rollback was needed.

Each node validates the artifact and existing capacity baseline, records private configuration/container state, stops admission, upgrades Claude Workers preserving identities/ports/volumes, deploys gateway and manager, verifies runtime hashes and performs real-model smoke tests. A failed node rolls back and prevents deployment of the next node. Codex and Gemini Worker instances are verified unchanged.
