**从订阅账号到企业内部 API：Codex App Server 网关建设技术难点工作汇报**

# 一、WebSocket 与 HTTP API 的协议转换

## 难度系数：★★★★★（5/5）

## **挑战点**：需要把一次性的 HTTP 请求，可靠地映射为有连接、账号、Thread 和多阶段事件状态的 app-server WebSocket 交互。

客户端非流式请求需要一次返回完整对象，SSE 请求要求按规定顺序输出创建、增量、完成或失败事件；app-server 却在 WS 上分别发送 Thread、Turn、内容增量、Token 用量、工具 RPC 和完成通知。一个连接还可能出现旧 Turn 的迟到事件。网络中断时，仅凭客户端没有收到响应，也无法断定上游没有执行，盲目重试可能造成重复回答、工具调用和额度消耗。

## **解决方案**：建立独立适配层管理 Thread、Turn 和事件生命周期，再转换成标准 API 对象。

网关在 `turn/start` 后记录当前 Turn ID，只接收属于当前 Thread 和 Turn 的通知；迟到事件被过滤，无关 RPC 被明确拒绝。非流式请求累积内容后统一返回，流式请求生成对应 API 的 SSE 序列和终态。只有确认 Turn 尚未开始时，池化请求才允许换 Worker 重试一次；已经输出、进入工具阶段或状态不明确时不自动重放。请求 ID、Worker、Thread、状态、耗时、用量和错误代码同时落库。

## **目前效果**：网关能够稳定提供 Responses、Chat Completions 的 JSON 与 SSE 接口，并避免跨 Turn 串流和状态不明时的重复执行。

客户端继续按 OpenAI API 的方式调用，无需理解 app-server RPC。成功、失败、工具调用和用量均能转换为客户端可识别的格式；故障时系统报告明确结果，不会擅自重复可能已经开始的 Turn。

# 二、WebSocket 并发池、工作目录与 Thread 隔离

## 难度系数：★★★★☆（4/5）

## **挑战点**：一条 WS 无法满足同一 Key 的并发请求，而无限创建连接又会耗尽 Worker 资源，并造成会话串线和工作目录混用。

并发测试表明，同一个 Key 可能同时运行多个任务，一个 Worker 也会承载多个 Key。共用一条 WS 会形成串行瓶颈，每次新建 WS 又会快速消耗连接和工作区资源。同时，Worker、WS 和 Thread 分别代表账号隔离、并发连接和对话上下文，生命周期不能混为一谈；WS 回收不应删除 Thread，同一 Thread 的两个 Turn 又不能并发。

## **解决方案**：实现按 Key 和 Worker 分组的连接池，分别管理连接、Thread 锁和工作区。

同一 Key 与 Worker 优先复用空闲 WS，未达到上限时按需新建；当前每组最多 10 条、单 Worker 最多 40 条，等待连接槽超过 30 秒返回 `worker_capacity_exceeded`，空闲 10 分钟自动回收。每条 WS 使用独立工作目录，同一 Thread 使用独立锁。Thread 可以通过原 Worker 上任意空闲 WS 恢复，连接回收、执行锁和长期会话绑定互相独立。

## **目前效果**：同一 Key 可以并发处理多个任务，单 Worker 连接资源有明确上限，WS 回收也不会破坏长期会话。

系统避免了“一 Key 一 WS”的串行瓶颈和无限连接，管理员也能清楚区分账号容器、并发通道与对话上下文。

# 三、逻辑会话聚合与后端 Thread 续接

## 难度系数：★★★★★（5/5）

## **挑战点**：不同客户端传递的会话线索不一致，缓存命中和相似历史也不能直接证明两个请求应恢复同一个后端 Thread。

早期主要依赖 `previous_response_id`，但 Codex CLI、Smartwork 等客户端并不总是稳定传递它。缓存命中只证明输入前缀相似，不能证明请求属于同一会话。我们扩充请求观测，对比各客户端携带的 thread、session、installation、turn、originator 和窗口标识，并进一步确认：页面统计聚合与真正恢复 Worker Thread 必须采用不同强度的证据。

## **解决方案**：先使用明确客户端身份寻找候选，再用历史前缀和配置一致性决定是否续接。

逻辑会话由 API Key、接口、客户端来源、安装标识和客户端 Thread 标识共同限定；IP、缓存命中、`prompt_cache_key` 和标题生成不授权续接。候选会话还要验证完整历史前缀、模型、instructions、工具和输出配置。通过时只提交新增用户内容；失败、绑定失效或 Thread 不存在时，用完整输入新建 Thread。绑定长期保留、按需验证，并在管理员释放、Key/Worker 删除或账号更换时失效；活动页只显示最近两小时，旧绑定和审计数据仍保留。

## **目前效果**：请求历史和活动会话使用一致的逻辑身份，符合条件时恢复原 Thread，不符合条件时安全重建。

会话可以跨 WS 回收长期恢复，又不会因缓存命中而错误串接。近期发现旧版指纹忽略工具结果图片、新版纳入图片的兼容问题，说明历史算法也需要版本化；旧版本应只用于验证旧前缀，重建成功后升级为当前版本。这是目前已定位、仍需完善的一项工作。

# 四、客户端工具、Grammar 与 Worker 安全边界

## 难度系数：★★★★★（5/5）

## **挑战点**：既要让 Codex CLI、Smartwork 完成结构化工具调用，又不能让客户端借工具声明在 Worker 上远程执行命令。

工具流程横跨两次 HTTP 请求：Worker 生成调用，客户端本地执行并用同一 `call_id` 返回结果，网关再唤醒挂起的 app-server RPC。期间必须保持 API Key、Worker、Thread、WS 和调用身份，并处理超时、重复、伪造与重启。grammar 工具还要求输入严格符合客户端语法，而 app-server 没有完全等价的原生约束；同时绝不能把客户端工具退化为 Worker 内置命令。

## **解决方案**：建立“网关转译、客户端执行、服务端验证”的工具桥接协议，并将客户端工具与 Worker 能力彻底分开。

网关把 function、custom 和 grammar 工具注册为动态函数，Worker 只生成调用，实际工具始终由客户端执行。结果必须匹配原 `call_id`，并校验 Key、会话、Worker、模型和工具配置；等待 5 分钟且只允许提交一次。grammar 在流开始前编译，生成后由固定版本 LLGuidance 完整匹配，不合法时在 Worker 内要求模型最多修正两次。解析进程限制输入、CPU、内存、并发和超时，不使用 `eval`、`exec`、Shell 或动态导入。每次执行重新应用服务端安全策略，拒绝客户端覆盖 cwd、sandbox、审批和权限。

## **目前效果**：主流客户端可以完成 function、custom 和 grammar 工具往返，同时 Worker 保持不可被客户端远程控制的隔离边界。

工具名称、参数、grammar 输入和调用 ID 可以完整往返，错误格式不再静默忽略。网关重启丢失挂起 RPC 时，系统要求完整历史和新的用户轮次重建 Thread，不会重复执行旧工具。

# 五、订阅账号池、Worker 隔离与故障恢复

## 难度系数：★★★★☆（4/5）

## **挑战点**：订阅账号不是天然的 API 后端，需要把登录、套餐限额、容器健康、账号更换和请求调度统一为可治理的 Worker 池。

WS 可连接不代表账号已经登录，`account/read` 正常也不代表仍有推理额度，一次业务失败也不能直接证明 Worker 损坏。隔离过于敏感会误伤正常账号，恢复过于宽松又会持续分配给异常账号。更隐蔽的是容器 ID 不变但内部账号已更换，此时若只按 Worker ID 恢复，可能把旧 Thread 交给新账号。

## **解决方案**：将账号身份、真实推理探测、隔离状态和调度条件组合成完整 Worker 生命周期。

系统读取登录、邮箱、认证类型、套餐和限额窗口，分别标记未登录、超限与服务异常。疑似故障需经过账号检查和最小真实推理确认，冷却后再次探测成功才恢复。池化 Key 只选择健康且有容量的 Worker；只有 Turn 尚未开始时才允许切换重试。账号身份使用递增 generation，换账号、强制重登或删除 Worker 会使旧绑定和租约失效。容器由独立 Worker Manager 管理，网关不持有 Docker Socket；Worker 使用非 root、只读根文件系统和资源限制。

## **目前效果**：系统可以维护多个订阅账号组成的可用池，自动区分登录、超限、服务异常和恢复状态，并防止账号切换后误续旧会话。

管理员可以查看账号、套餐、限额、隔离原因和恢复结果；单个账号故障不会拖垮整个池，账号变更也不再只凭容器 ID 判断续接。

# 六、贡献 Worker、Key Quota 与池用量监控

## 难度系数：★★★★☆（4/5）

## **挑战点**：需要把用户贡献的订阅账号转换为公平、可并发校验且可自动收回的内部额度，同时提供可解释的账号池风险指标。

按 Worker 数量发放额度，会让同一账号通过多个容器重复获得名额；Worker 退出、停用或转移后，Key 还可能继续超额，并发创建和启用也可能越过页面校验。另一方面，不同账号的 5 小时与周窗口重置时间并不一致，不能简单相加，却仍需形成可理解的池风险指标。

## **解决方案**：将有效账号贡献、管理员授予额度和 Key 占用统一为事务化 quota，并独立采集带权重的风险快照。

总 quota 等于管理员授予额度加有效付费账号贡献，Key 启用时占用、停用时释放；同一用户按完整账号邮箱去重。Worker 登录、退出、停用、删除、转移、换号和健康变化都会重算额度，下降时按从未使用、最久未使用的顺序停用超额 Key。相关写入使用 PostgreSQL 事务锁防止并发超额。监控每 10 分钟采集状态、每小时采集限额，按套餐权重估计池风险；不同重置窗口不伪装成统一账期，失败样本只标记缺失。

## **目前效果**：用户可以通过贡献有效订阅账号获得 Key 名额，重复账号不重复计数，资源变化后额度自动回收和恢复。

自助页面形成“贡献 Worker—生成 Key—定期维护”流程，管理端可查看五类状态、限额风险、覆盖率和历史趋势；一次监控失败不会误停服务。

# 七、订阅能力模拟原生 API 的功能边界与计量

## 难度系数：★★★★☆（4/5）

## **挑战点**：需要尽量兼容原生 OpenAI API，同时诚实处理 app-server 无法提供的能力，并把订阅用量转换为可审计的 API 等价成本。

“字段可以接收”不等于“功能兼容”。service tier、stop、输出 Token 上限或 logprobs 如果没有上游能力，返回成功会让客户端误以为已经生效。计量也不能只记录输入输出总量：Thread 用量可能是累计值，工具又会把一个 Turn 拆成多个 HTTP 段，直接累加会重复计费；缓存读写虽然属于输入 Token，价格却可能各不相同。

## **解决方案**：以真实语义而不是字段数量定义兼容范围，并为每个 Turn、每笔请求保存四项用量和价格快照。

网关只把参数真实影响上游或响应语义真实的能力视为兼容，无法兑现的重要参数明确拒绝。目前支持 Bearer、Models、Responses、Chat Completions、JSON/SSE、URL/Data URL 图片、Reasoning effort、Structured Outputs、客户端工具、会话恢复和 OpenAI 风格错误。用量从当前调用或累计差值中提取普通输入、输出、缓存读和缓存写，避免工具续接重复累计；每笔请求保存四项用量、单价和费用快照，报表可按最新价格重算 API 等价成本并与订阅月费比较。

## **目前效果**：系统可以满足内部文本、图片、结构化输出、工具和多轮会话等主要自动化需求，也能准确展示与原生 API 的差异。

当前仍不等同于原生 API：后台任务、持久化响应查询、取消、幂等键、多候选输出、logprobs、音频、文件、真实 service tier、精确 stop、输出 Token 上限和部分推理明细尚未实现或受上游限制。系统适合作为内部受控工作流的统一入口，而不是原生 API 的无差别替代品。
